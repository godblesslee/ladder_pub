# 啤酒测评活动 App PRD

## 1. 项目背景

当前线下啤酒测评活动依赖纸质表格记录。纸质流程的问题主要在于：

- 现场填写与后续汇总效率低
- 用户的测评记录难以长期沉淀
- 同一酒款在不同活动中的感受无法被系统化记录
- 组织者难以复用模板、管理酒款资料和活动内容
- 用户之间的分享内容无法自然形成传播与讨论

本项目希望把纸质测评表升级为适用于活动现场的数字化应用，并兼顾用户留存与轻量社交。

## 2. 产品目标

### 2.1 业务目标

- 支撑线下啤酒测评活动的数字化填写与管理
- 建立酒款基础数据库，提升活动组织效率
- 建立用户个人品鉴档案，提高复购与留存
- 形成可浏览的公开评价内容，增强社区感与传播性

### 2.2 产品目标

- 用户能在活动中快速完成逐款测评
- 主办方能灵活维护测评模板，而不是每次改代码
- 支持同一用户在不同活动中对同一酒款产生多条独立测评记录
- 用户能方便回看自己参加过的活动和喝过的酒

## 3. 核心角色

### 3.1 普通用户

- 浏览已上线活动与未来活动
- 查看并参与自己报名/受邀的活动
- 在活动中对酒款完成测评
- 查看自己历史测评过的酒款和活动
- 发布公开可见的评论/感受/故事

### 3.2 活动组织者

- 创建和维护活动
- 维护酒款数据库
- 为活动选择待测评酒款
- 维护测评模板
- 查看活动数据与用户提交情况

### 3.3 管理员（可与组织者角色合并）

- 管理组织者权限
- 管理系统级模板与酒款数据规范

## 4. 核心场景

### 4.1 活动前

- 组织者创建活动
- 组织者从酒款数据库中选择本场活动的酒款
- 组织者选择或复制一个测评模板
- 活动上线后，用户在 App 中能看到未来活动

### 4.2 活动中

- 用户进入某场活动
- 查看本场待测评酒款列表
- 逐款进入测评页面，填写感知项、总分与文字分享
- 提交后可继续下一款，也可回看已填写内容

### 4.3 活动后

- 用户回看自己的测评记录
- 用户查看同场其他用户公开分享
- 组织者复盘活动数据

## 6. 功能需求详述

### 6.1 首页/发现页

首页应优先采用 App 式移动端结构，而不是传统网页式介绍页。

展示三个核心模块：

- 已上线的活动（含未来即将开始的活动）
- 我参与的活动
- 我测评过的酒款

导航要求：

- 页面底部固定保留 Tab Bar
- Tab Bar 至少包含：首页、活动、酒单
- 用户上下滑动内容时，底部导航不能消失
- 进入活动详情时，“活动”Tab 应保持激活态
- 进入酒款详情 / 测评详情时，“酒单”Tab 应保持激活态

排序要求：

- 我参与的活动：按活动时间先后排序
- 我测评过的酒款：按用户给出的总评分从高到低排序

### 6.2 活动模块

活动列表字段建议包含：

- 活动名称
- 活动时间
- 活动地点
- 封面图
- 活动状态（未开始/进行中/已结束）
- 本场测评酒款数量

活动详情页应包含：

- 活动基本信息
- 本场酒款列表
- 用户自己的完成进度

### 6.3 酒款模块

酒款基础库字段至少包括：

- 厂牌
- 产品名称
- 啤酒类型
- 容量
- 国别
- 酒精度
- 图片

活动中的酒款应允许附加活动内信息：

- 出场顺序
- 当场备注
- 是否盲评
- 供应批次/年份（如有）

### 6.4 测评模块

每条测评记录必须绑定三个核心对象：

- 用户
- 活动
- 酒款

测评内容分为四类：

- 模板结构化选项
- 总评分
- 公开分享文字
- 私密备注（可选，供用户自己留档）

重要规则：

- 同一用户在不同活动中遇到同一酒款，必须允许生成多条不同测评记录
- 模板项以“感受记录”为主，不以分项数值打分为主
- 公开文字内容可被其他用户查看

### 6.5 我的酒款库

用户可以看到自己测评过的每一款酒，但数据展示要基于“测评记录”而不是“酒款唯一值”。

建议支持两种视图：

- 按测评记录查看：一场活动中的一次测评是一条记录
- 按酒款聚合查看：同一酒款可显示曾参加过几次相关活动、给过几次评分

### 6.6 模板管理

模板不应写死在前端代码中，而应由后台配置。

模板应支持：

- [x] 分组（sections）
- [x] 单选（single_select）
- [x] 多选（multi_select）
- [x] 文本输入（textarea）
- [x] 数值评分（number）
- [x] 排序（sort）
- [ ] 是否必填（field.required）

后台配置路径：/admin/templates

## 7. 非功能需求

### 7.1 设备与体验

- 以手机端 Web 为优先
- 现场填写路径应尽量短
- 每款酒的测评页面要适合单手操作和快速提交
- UI 视觉应尽量接近成熟 App，而不是传统网页后台
- 留白、层次、间距、卡片表面和底部导航需要保持一致的设计语言
- 表单选项组件的视觉样式必须统一，不能混用默认浏览器 radio / checkbox 外观

### 7.2 性能

- 首页、活动列表、酒款详情等关键页面应在弱网环境中保持可用
- 图片应支持压缩与懒加载

### 7.3 数据安全

- 用户只能编辑自己的测评记录
- 用户仅能看到公开发布的他人评论
- 组织者仅能管理自己所属活动数据

## 8. 成功标准

MVP 上线后的初步成功指标建议：

- 用户能在一次活动内顺畅完成至少 5-10 款酒的测评
- 组织者可独立创建活动并配置模板
- 用户能稳定回看自己的历史记录
- 同场活动内的公开评论可被正常浏览

## 9. MVP 边界

MVP 不优先处理：

- 复杂的社区关系
- 多级评论互动
- 推荐算法
- 高度复杂的报名/支付流程
- 原生 App 打包

## 10. 开发原则

- 先做可用，不先做过度复杂的社区玩法
- 模板配置化优先级高于页面视觉复杂度
- 记录的可追溯性优先于花哨评分体系
